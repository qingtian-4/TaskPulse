# 执行阶段与误完成提醒：诊断、修复、验证

## 这次暴露的设计问题

1. 原上游交叉验证仍把旧 Hook + 低 CPU 改成 Idle；云端思考恰好也低 CPU。过渡引擎又将 Running→Idle/任务消失当成完成，并在 Idle→Running 清除通知记忆，于是长任务可以反复收到“可能已结束”。这是证据层级和生命周期边界错误，不是刷新频率问题。
2. `activity` 混用了当前工具和上一个工具。Codex 的 `custom_tool_call_output` 原来未处理，普通 output 也只处理用户提问的返回；Claude 的 PostToolUse 仍复制已结束指令。思考事件又没有独立展示字段。
3. Claude 截图的失败项和成功对话不是同一个 ID。成功审查对话原生标题为“当前使用的模型”；“hello”是另一条认证失败历史。v3 曾把旧未完整日志冷启动成 Running，再在后续修正为 Failed，错误地更新关注活动时间。
4. Store 单纯按置信度排序可能让上一轮 Hook 状态压住新一轮原生观测。适配器已经合并过 Hook/日志，不能把它的较新同会话状态当成另一个竞争数据源。

## 修改后的不变量

- 思考、生成回复、执行工具、等待模型响应属于同一活动 turn。工具返回不是 turn 结束。
- 原生适配器按稳定 call ID 保留未返回工具，并行调用不相互覆盖；结束时清除当前命令。只有明确阶段证据才显示“正在思考”，否则明确显示等待响应/阶段不可用。不读取/展示思考正文。
- 进程扫描不能覆盖结构化会话/Hook 生命周期；CPU、静默、文件缺失不触发 Agent 完成提醒。缺少观测保留状态并标记待更新。
- 同一 turn 的状态抖动不能重置提醒去重。不同 turn、新的明确问题仍独立提醒；记录跨重启保留。
- 普通 tmux 的明确 shell-return 结束快照仍可推断结束。无退出码时不标“成功”。Agent 会话不使用“可能已结束”推断。
- 新鲜且时间不倒退的同来源实例/同原生会话观测可以推进状态；跨来源和普通 tmux 保留置信度优先规则。
- 首次启用不导入无原生未读证据的失败/阻塞历史。v4 对符合旧误导入时间特征的 Claude 失败项做保守归档，保留未读、真实错误、固定标记；手动关注/固定优先，新 turn 恢复。**不把其他会话的成功当成本会话成功，不批量清未读。**
